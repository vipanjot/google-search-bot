## 🔐 Security Rules

Claude must follow these rules in **every session** without exception.

### Never Expose

- API keys, tokens, secrets, or passwords — not in code, comments, or logs
- MongoDB connection strings or credentials
- Firebase service account keys or config secrets
- JWT secrets or session secrets
- User PII (emails, names, IDs) hardcoded anywhere
- Internal server paths or stack traces in client-facing error responses

### Environment Variables

- All secrets live in `.env` files — **never hardcoded**
- Frontend (Vite): only use `VITE_` prefix for non-sensitive config (e.g. public Firebase config)
- Backend: sensitive keys (MongoDB URI, Firebase Admin SDK, etc.) live only in backend `.env`
- Always maintain `.env.example` with placeholder values — this **can** be committed

```bash
# .env.example (safe to commit — placeholders only)
MONGODB_URI=your_mongodb_connection_string_here
FIREBASE_PROJECT_ID=your_firebase_project_id_here
FIREBASE_PRIVATE_KEY=your_firebase_private_key_here
PORT=5000
```

### Firebase Auth Rules

- Verify Firebase ID tokens **on the backend** using Firebase Admin SDK — never trust the client
- Attach decoded user info to `req.user` via middleware
- Never expose Firebase Admin credentials to the frontend

### Code Practices

- Validate and sanitize all user inputs on the backend
- Never trust data from the frontend — always re-validate server-side
- Use Mongoose schema validation as a first line of defense
- Return generic error messages to clients — never expose stack traces in production
- CORS: whitelist specific origins only — never use `*` in production
- Keep auth checks in middleware, not scattered across route handlers

## ✅ Coding Standards

### General

- **Always write comments** — explain the *why*, not just the *what*
- Write clean, readable code over clever one-liners
- Functions should do one thing only
- Name variables and functions descriptively — no `x`, `temp`, `data2`

```js
// ✅ Good — explains intent
// Verify the Firebase token before allowing access to protected routes
const verifyToken = async (req, res, next) => { ... }

// ❌ Bad — no context
const vt = async (r, s, n) => { ... }
```

### React (Frontend)

- Functional components only — no class components
- Extract reusable logic into custom hooks (`useAuth`, `useFetch`, etc.)
- Keep components under ~150 lines — split if larger
- API calls go in `services/` — never directly inside components
- Context is for global state (auth, theme) — don’t overuse it for local state

### Express (Backend)

- One responsibility per route handler — delegate logic to controllers
- All async route handlers wrapped in try/catch or a global error handler
- Log errors server-side with full context; return a safe generic message to client
- Use middleware for: Firebase token verification, rate limiting, input validation

```js
// ✅ Correct pattern — auth in middleware, logic in controller
router.get('/profile', verifyToken, userController.getProfile)
```

### MongoDB / Mongoose

- Define strict schemas — avoid untyped or schema-less collections
- Use `.lean()` for read-only queries (better performance)
- Never expose raw `_id` or internal fields unless intentional
